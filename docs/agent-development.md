# Agent development operating model

This inventory records the instructions, responsibilities, and deterministic
controls used by development agents working on Mega Agents. It distinguishes
what the repository enforces today from behavior that is only documented or
still needs a defined mechanism. Keep the always-visible policy concise; put
detailed, reusable workflows in skills and link to them from adapters.

This document describes the target operating model, but it does not itself make
a control effective. A row is green only when the stated capability exists at
the scope claimed. Repository policy gates are catalogued separately in the
[CI guardrail inventory](ci-doc.md) and operated through the
[custom gates guide](custom-gates.md).

Status: ✅ implemented · 🟡 partially implemented · ⬜ not implemented.
Value: 🏆 independently marks a highest-value foundation or next investment;
an unmarked row is not a claim that the capability is unimportant.

## Agent evaluation

One deterministic, diagnosis-only scenario runs the selected agent tool with
an explicitly selected model in a disposable Git worktree:

```sh
make agent-eval TOOL=opencode MODEL=opencode-go/glm-5.3-flash
```

To evaluate another model or agent configuration, replace the
`MODEL=provider/model` value. Add `VARIANT=high` when the provider and model
support that reasoning variant.

The evaluation checks required workflow and instruction discovery, focused
failure reproduction, correct root-cause diagnosis, no file changes, and no
unauthorized fix. Passing requires all five criteria and a zero agent exit
status. Results default to `reports/agent-eval/result.json`; test the
deterministic runner with `go test ./internal/agenteval`.

Install and authenticate OpenCode before a real run. `OPENCODE` overrides the
executable path and `RESULT` overrides the JSON destination. A passing run exits
zero, a completed but failing evaluation exits one, and configuration or runner
failures exit two. The report captures the raw OpenCode JSON-lines transcript,
extracted final text and tool results where available, process exit status,
duration, and pre/post Git status, binary diff, and content digests. Real model
runs are manual; required CI uses a fake OpenCode executable and incurs no model
cost.

This first scenario demonstrates one narrow capability; it does not establish
that a model is suitable for the whole project. Broader scenarios and repeated
runs remain roadmap work (priorities 1 and 2 below). OpenCode is the only
implemented tool adapter; Claude, Codex, Grok, and other adapters remain future
work.

Compatibility is not automatic for arbitrary tools. A tool is compatible only
when it supports `AGENTS.md` and Agent Skills directly or has an adapter that
preserves the canonical instructions and invocation boundaries.

The roadmap does not recommend persona-style roles, mandatory multi-agent
execution, a heavyweight issue-tracker workflow, or automatic commits, pushes,
or merges. Paid or nondeterministic model calls should not become required merge
gates unless later evidence shows that their value and reliability justify the
cost and operational dependency.

## Updating this inventory

Update this page when agent instructions, adapters, collaboration conventions,
compatibility evidence, or their enforcement changes. A status should advance
only when the mechanism covers the full claim in that row. A trophy should move
only when relative value changes, independently of implementation status.
Changes to CI-defining files still follow the separate update rules in
[`ci-doc.md`](ci-doc.md); editing this inventory does not satisfy the
CI-documentation drift gate.
